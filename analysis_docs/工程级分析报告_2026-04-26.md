# LZ Sports 工程级分析报告

**生成日期**: 2026-04-26
**分析范围**: Spring Boot 3.2.3 + Vue 3.5 前后端分离项目
**分析方法**: 基于代码结构、依赖、配置文件、SQL Schema、Git 历史的静态审计

> **缺失信息声明**: 本报告未执行运行时性能测试、数据库慢查询分析、渗透测试。以下信息在当前代码库中不可得：生产环境实际 QPS、数据库索引实际状态、线上流量模型、APM 数据。所有结论均标注了推导依据。

## 1. 项目整体架构分析

### 架构模式

**前后端分离单体应用**，非微服务。

| 维度 | 判定 | 依据 |
|------|------|------|
| 部署形态 | 单后端 + 单前端 | `BackendApplication.java`（单一启动类），Vite 单入口构建 |
| 代码组织 | 单体多模块 | 无独立 Maven module，仅按 package 分包 |
| 数据库 | 单库 12 张表 | `resources/sql/lz_sports.sql` 包含全部 DDL |
| 容器化 | Docker Compose + K8s 均支持 | `docker-compose.yml` / `docker-compose.prod.yml` / `k8s/` |

### 分层设计

**整体清晰，存在局部穿层**：

```
┌──────────────────────────────────────────┐
│  Controller (14个)                        │  ← 薄层，参数接收 + Result 包装
├──────────────────────────────────────────┤
│  Service / ServiceImpl (13组)             │  ← 核心逻辑 + 事务管理
├──────────────────────────────────────────┤
│  Mapper (14个) + XML (5个)                │  ← MyBatis-Plus BaseMapper
├──────────────────────────────────────────┤
│  Entity (15) / DTO (15) / VO (18)        │  ← 三层数据对象分离
└──────────────────────────────────────────┘
横切关注点：
├── Aspect (PermissionAspect)         → 注解驱动的角色/赛事权限校验
├── Filter (JwtAuthenticationFilter)  → Token 校验 + ThreadLocal 上下文
├── Exception (GlobalExceptionHandler) → 9 种异常类型的全局处理
└── Config (6个)                      → Security/MyBatis-Plus/Redis/Web/Swagger
```

**依据**：
- Controller 平均 ~40 行，未发现业务逻辑（如 `AdminUserController.java:20-52`、`AthleteController.java:20-102`）
- Service 是唯一的业务逻辑承载层，包含校验、事务、通知
- Mapper 全部继承 `BaseMapper<T>`，复杂 SQL 在 XML 中（如 `RegistrationMapper.xml`）

### 模块边界

| 模块 | 边界 | 评估 |
|------|------|------|
| 认证鉴权 | JWT Filter + AOP + SecurityConfig 三层 | ✅ 职责分散但各司其职 |
| 赛事管理 | Event + Project + EventAdminMapping | ✅ 实体关系清晰，状态机独立 |
| 报名管理 | Registration + Redisson 分布式锁 | ✅ 独立的并发控制 |
| 成绩管理 | Score + ScoreAuditLog + Excel 导入导出 | ✅ 发布机制 + 审计 |
| 通知 | Notification + NotificationService | ✅ 独立服务 |
| 用户管理 | UserServiceImpl 582行 | ⚠️ **边界模糊**：混合了注册、登录、密码重置、统计、列表、角色审计 |

### "伪分层"与"上帝类"

- **UserServiceImpl**（582行）是轻度上帝类——同时承担 6 种不同职责：注册、登录、密码重置、用户列表、统计查询、审计日志写入。依据：`UserServiceImpl.java:58-582`
- **EventServiceImpl**（791行）行数多但职责集中（赛事 CRUD + 状态变更 + 管理员绑定），所有方法围绕 Event 实体。不算上帝类
- **ScoreServiceImpl**（589行）职责集中在成绩管理
- **不存在伪分层**——未发现 Controller 直接调用 Mapper、Service 返回 Entity 等情况

### 事务管理

| 模式 | 位置 | 评估 |
|------|------|------|
| `@Transactional(rollbackFor=Exception.class)` | 所有写操作 Service 方法 | ✅ 覆盖 checked exception |
| Redisson 分布式锁 | `RegistrationServiceImpl.add()` | ✅ 幂等令牌（5s）+ 双层锁（用户+赛事/项目） |
| `SELECT ... FOR UPDATE` | `UserServiceImpl.updateUser()` 中 `selectByIdForUpdate` | ✅ 悲观锁防并发修改 |
| 嵌套事务 `REQUIRES_NEW` | `RegistrationServiceImpl.syncAthleteProfileToUser()` | ✅ 异步同步，独立事务 |

**缺失**：
- `EventServiceImpl.deleteEvent()`（第380-428行）在 `@Transactional` 内混合了多个 Mapper 操作——先判断 `scoreCount > 0` 再执行删除，判断和执行之间存在时间窗口，可能被并发写入击穿
- 未发现全局事务超时配置

### 异常处理

**设计良好**（`GlobalExceptionHandler.java:29-123`）：

```
BindException / MethodArgumentNotValidException / ConstraintViolationException
  → 400 (参数校验)
SQLIntegrityConstraintViolationException
  → 409 (数据冲突)
SQLException
  → 500 (数据库错误，含 e.getMessage())
BusinessException
  → 自定义 code + message
AccessDeniedException
  → 403 (解析 @PreAuthorize 注解给出精准权限提示)
NoResourceFoundException
  → 404 (过滤 Swagger/favicon 噪音)
Exception (兜底)
  → 500 (含 e.getMessage())
```

**风险点**：`SQLException` 和 `Exception` 兜底处理器直接返回 `e.getMessage()` 给前端——生产环境可能泄露内部表名/字段名。

### 典型反模式

| 反模式 | 是否存在 | 证据 |
|------|---------|------|
| Controller 过重 | ❌ | Controller 均为薄层，未发现业务逻辑 |
| Service 膨胀 | ⚠️ 部分 | UserServiceImpl(582行)、EventServiceImpl(791行) |
| Mapper 直出业务逻辑 | ❌ | Mapper 仅做数据访问，逻辑在 Service |
| `@Autowired` vs `@RequiredArgsConstructor` 混用 | ⚠️ | UserServiceImpl 使用 `@Autowired`，EventServiceImpl/ScoreServiceImpl/RegistrationServiceImpl 使用 `@RequiredArgsConstructor`——**风格不一致** |
| Date 使用 SimpleDateFormat | ⚠️ | EventServiceImpl 每次新建实例，正确但低效（`EventServiceImpl.java:618-623`） |

**字段兼容问题**（`stores/user.js:13-22`）：
```javascript

  const role = normalized.role || normalized.type || normalized.userType
  if (role) {
    normalized.role = role
    normalized.type = role
    normalized.userType = role

```
三个字段名回退逻辑 → **后端 JWT claims 中角色字段名曾不稳定**。路由守卫（`router/index.js:244`）同样做了三字段回退。这是技术债信号。

### 路由设计

**22 条路由，分层管理**：

| 类型 | 数量 | 机制 |
|------|------|------|
| 公开路由 | 6 | login/register/portal/init/forgot-password/401/403/404/500 + 通配 |
| 需登录（无角色限制） | 7 | dashboard/event/profile/registrations/notifications/scores 等 |

**路由守卫 5 步处理链**（`router/index.js:195-253`）：
1. 系统初始化检查（如果未初始化，强制跳 /init）
2. Token 存在性检查
3. 已登录但访问 login/register → 重定向 dashboard
4. 首次登录强制改密（`isFirstLogin` 跳 /reset-password）
5. 角色权限检查（`meta.roles`）

**设计正确**：前端角色校验仅隐藏 UI，后端 AOP 注解是真正的安全边界。

### API 调用封装

**设计规范**（`utils/request.js:40-102`）：

- 统一 Axios 实例：`baseURL: '/api'`，`timeout: 10000ms`

**策略模式**（`config/errorStrategy.js:1-45`）：
```

403 → redirect /403（保留登录态）
404 → redirect /404
500 → redirect /500
504 → 仅 warning，不跳转
```
`before` 回调均未使用——扩展点存在但未被利用。

`apiRequest()` 工厂函数支持 meta 操作名（用于错误提示个性化），但当前 API 调用中未发现实际使用。

## 4. 前后端交互设计

### API 设计风格

**混合风格，趋向 RESTful**：

| 模式 | 示例 | 符合 REST? |
|------|------|-----------|
| 标准 REST | `GET /api/admin/users`, `PUT /api/admin/users/{id}/role` | ✅ |
| 非标准动词 | `POST /api/admin/users/{id}/disable` | ❌ 应为 `PATCH` + body 含 status |
| RPC 风格 | `POST /api/auth/send-code` | ⚠️ 认证场景可接受 |
| 统计接口混在业务路径 | `GET /api/auth/getNums` | ❌ 语义不匹配（auth 下做统计） |

### DTO / VO 规范

**三层分离明确**：

```
请求: 前端 → DTO → Controller → Service
响应: Service → VO → Controller → Result<T> → 前端
持久层: Entity → Mapper → DB
```

- DTO 15个（请求输入，如 `UserLoginDTO`, `ScoreUpsertDTO`）
- VO 18个（响应输出，如 `UserLoginVO`, `ScoreVO`, `EventVO`）
- Entity 15个（数据库映射，含 `BaseEntity` / `SchoolRelatedEntity` 继承链）

### 错误码体系

**统一但薄弱**（`ResultCode.java:1-27`）：

```
200  SUCCESS
400  PARAM_ERROR
401  UNAUTHORIZED
403  FORBIDDEN
404  NOT_FOUND
409  CONFLICT
500  INTERNAL_SERVER_ERROR
```

- 复用 HTTP 状态码作为业务码，直观 **但有代价**：
  - 所有业务冲突统一返回 409，前端无法区分"用户名已存在" vs "邮箱已注册"
  - 缺少子错误码体系

### 鉴权方式

**JWT + Redis 双重校验**：

1. 登录 → 生成 JWT（12h过期）→ 存入 Redis `auth:token:{userId}`（7天）
2. 每次请求 → JWT Filter → 解析 token → Redis 校验存在性 → 设 SecurityContext
3. 改密/禁用/登出 → 删除 Redis key → 即使 JWT 未过期也无法通过 Redis 校验

**设计优点**：支持服务端主动失效。**代价**：每次请求多一次 Redis 查询。

## 5. 数据流 & 关键链路分析

### 完整调用链：运动员报名

```
前端: event/detail.vue → 点击"立即报名"
  │
  ▼
POST /api/registration/{projectId}
  Header: Authorization: Bearer <token>
  │
  ▼
JwtAuthenticationFilter.doFilterInternal()          [过滤器]
  │ 1. isPublicPath? → 否
  │ 2. extractToken() → Authorization header
  │ 3. JwtUtil.isExpired() → 签名+过期校验
  │ 4. JwtUtil.parseToken() → 解析 claims
  │ 5. Redis 二次校验: redisUtil.get("auth:token:" + userId) == token?
  │ 6. enforceFirstLoginPasswordReset() → 首次登录强制改密检查
  │ 7. BaseContext.setCurrentId(userId) → ThreadLocal
  │ 8. SecurityContextHolder.setAuthentication()
  │
  ▼
RegistrationController.add(projectId)               [Controller - 薄层]
  │
  ▼
RegistrationServiceImpl.add(projectId)              [Service - 核心逻辑]
  │
  ├── [CP1] BaseContext.getCurrentId() → 获取用户
  ├── [CP2] Redisson 幂等令牌: "registration:idempotency:{uid}:{pid}" (5s TTL)
  │
  ├── [CP3] Redisson 分布式锁: "registration:lock:user_event:{uid}:{eid}"
  │   └─────────────────────────────────────────────
  │   ├── [CP4] Redisson 分布式锁:                   嵌套锁
  │   │   "registration:lock:project:{pid}"         ⚠️ 死锁风险点
  │   │
  │   ├── [CP5] userMapper.selectById(userId) → 用户信息
  │   ├── [CP6] athleteMapper.selectOne(userId, eventId) → 运动员资格
  │   ├── [CP7] registrationMapper.lockAthleteRowForEvent() → DB行锁(兜底)
  │   │
  │   ├── 业务规则校验链:
  │   │   ├─ 赛事状态 == OPEN?
  │   │   ├─ 报名窗口内? (assertWithinRegistrationWindow)
  │   │   ├─ 重复报名检查
  │   │   ├─ 超 maxItemsPerAthlete?
  │   │   ├─ 时间冲突检查 (findConflictItemName)
  │   │   ├─ 性别限制检查
  │   │   └─ 部门限制检查 [CP8] ↓
  │   │       └─ departmentService.list() ← 全表扫描!
  │   │
  │   ├── [CP9] projectMapper.incrementAttendance(projectId, maxAttendance)
  │   │   └─ UPDATE event_item SET current_count = current_count + 1
  │   │      WHERE id = ? AND current_count < maxAttendance
  │   │
  │   └── [CP10] registrationMapper.insert() → 写报名记录
  │
  └── [CP11] @Async syncAthleteProfileToUser() → 异步同步用户资料
      └─ @Transactional(REQUIRES_NEW) → 独立事务
  │
  ▼
Response: Result<String> = { code: 200, msg: "成功", data: "报名成功" }

DB 操作汇总: 1次Redis幂等 + 2次Redis锁 + 1次用户查询
           + 1次运动员查询 + 1次DB行锁 + N次规则校验查询
           + 1次UPDATE计数器 + 1次INSERT报名记录
           + 1次异步UPDATE用户资料
```

### 耦合点分析

| 编号 | 耦合类型 | 风险 | 说明 |
|------|---------|------|------|
| CP2 | 幂等令牌 | ✅ | 防重复提交，5s 是合理窗口 |
| CP3+CP4 | 嵌套分布式锁 | ⚠️ **中风险** | `user_event` 锁覆盖整个赛事维度。1000人同时报名同一赛事 → 串行化。嵌套锁增加死锁风险（虽然当前释放顺序正确） |
| CP7 | DB 行锁兜底 | ✅ | 防止分布式锁失效时的并发写入 |
| CP8 | 全表扫描部门 | ⚠️ **中风险** | 每次报名加载全部部门数据到内存遍历匹配 |
| CP9 | 计数器更新 | ⚠️ | 依赖分布式锁保证原子性，天然限制并发 |
| CP11 | 异步同步 | ✅ | `@Async` + `REQUIRES_NEW`，不阻塞主流程 |

### 潜在性能瓶颈

1. **嵌套分布式锁串行化**：同一赛事的报名请求被 `user_event` 锁串行化。单次请求处理 < 100ms 时影响可控，但峰值 QPS 受限于此

2. **部门全表扫描**（`RegistrationServiceImpl.java:200`）：`departmentService.list()` 在分布式锁内执行。部门表通常几百条，短期影响小；但每次报名都做，属于不必要的浪费

3. **通知在事务内**：`publishEventNotification()` 在 EventServiceImpl 中逐用户创建通知。如果有 10000 个用户，发布赛事时会产生 10000 次 INSERT——虽然不在报名路径上，但是独立风险

4. **N+1 图片查询**（`EventServiceImpl.list():264-283`）：列表页每条 Event 循环查询图片

### 可优化点（具体到代码行）

| 优化项 | 位置 | 方案 |
|------|------|------|
| 部门缓存 | `RegistrationServiceImpl.java:200` | Caffeine 本地缓存 5min 过期 |

## 9. 问题清单（按严重程度排序）

### [严重] 1. 开发环境 Redis 密码硬编码

- **影响**：任何可访问代码仓库的人能获取 Redis 密码，攻击开发/测试环境
- **原因**：`application-dev.yml:11`：`password: ${REDIS_PASSWORD:!Theworld1949}`
- **修改建议**：改为 `${REDIS_PASSWORD:}`（空默认），通过 `.env` 文件注入；立即轮换已暴露密码

### [严重] 2. JWT 弱默认密钥

- **影响**：环境变量 `JWT_SECRET` 未设置时，使用 `lz_sports_secret_key` 作为签名密钥——攻击者可伪造任意用户 JWT
- **原因**：`JwtAuthenticationFilter.java:41` 和 `AppConfig.java:12` 中的 `@Value` 默认值
- **修改建议**：移除默认值，启动时校验 `jwt.key` 不为 null 且长度 ≥ 256 bits，否则拒绝启动

### [高] 3. CORS 配置违反安全规范

- **影响**：`allowCredentials(true)` + `allowedOriginPatterns("*")` 组合允许任意网站携带 Cookie 跨域请求
- **原因**：`SecurityConfig.java:108`
- **修改建议**：改为具体域名白名单：`setAllowedOriginPatterns(List.of("http://localhost:5173", "https://yourdomain.com"))`

### [高] 4. 全局异常泄露内部信息

- **影响**：`SQLException` 和 `Exception` 的 `e.getMessage()` 可能包含表名、字段名，泄露给前端
- **原因**：`GlobalExceptionHandler.java:76,122`
- **修改建议**：生产环境返回通用"服务器错误"消息，详细错误仅记录日志

### [高] 5. 生产日志打印全量 SQL

- **影响**：`application.yml:138-139` 全局 `com.lz.mapper: debug`，生产环境打印所有 SQL + 参数
- **原因**：未按 profile 区分日志级别
- **修改建议**：将 `com.lz.mapper: debug` 移到 `application-dev.yml`，生产设为 `warn`

### [中] 6. N+1 查询

- **影响**：每页 20 条记录产生 20 次额外 SQL；10 个并发列表请求 → 200 次额外 SQL
- **位置**：`EventServiceImpl.list():266`（循环查图片）、`ScoreServiceImpl.toScoreVO():537-557`（三次独立批量查询）
- **修改建议**：图片查询用 `selectBatchIds` 批量；Score VO 用 SQL JOIN 或一次查询

### [中] 7. 部门全表扫描在分布式锁内

- **影响**：每次报名加载全部部门数据到内存；与分布式锁的持有时间叠加
- **位置**：`RegistrationServiceImpl.java:200`
- **修改建议**：添加 Caffeine 本地缓存（5分钟过期），部门数据变更低频

### [中] 8. 定时任务无分布式互斥

- **影响**：多实例部署时 `EventStatusScheduler.refreshEventStatusesAutomatically()` 重复执行
- **原因**：Spring `@Scheduled` 不提供集群互斥
- **修改建议**：添加 ShedLock 或 Redisson 分布式锁

### [中] 9. @Autowired 与 @RequiredArgsConstructor 风格不一致

- **影响**：`@Autowired` 的字段不能声明为 final，降低可测试性
- **位置**：`UserServiceImpl.java:59-101`（12个 `@Autowired` 字段）
- **修改建议**：统一改为 `@RequiredArgsConstructor` + `private final`

### [中] 10. 通知发布逐条插入

- **影响**：发布赛事向 10000 个用户发通知 → 10000 次 INSERT
- **位置**：`EventServiceImpl.publishEventNotification():709-718`
- **修改建议**：使用 MyBatis-Plus `saveBatch()` 批量插入，或改为异步 + 消息队列

### [低] 11. 前端角色字段三次回退

- **影响**：`normalizeUserInfo` 同时设 role/type/userType 三个字段，增加维护混乱
- **位置**：`stores/user.js:14` 和 `router/index.js:244`
- **修改建议**：统一后端 JWT claims 中的角色字段名为 `role`，前端移除回退逻辑

### [低] 12. 缺少业务子错误码

- **影响**：所有业务冲突返回 409，前端无法精确区分
- **位置**：`ResultCode.java` 仅 7 个枚举值
- **修改建议**：引入子错误码（如 `40901` 用户名重复），或保持现状（当前规模可接受）

### [低] 13. fastjson2 冗余依赖

- **影响**：无功能影响，仅增加 jar 体积和潜在 CVE 面
- **位置**：`pom.xml:84-86`
- **修改建议**：移除（代码未实际使用）
