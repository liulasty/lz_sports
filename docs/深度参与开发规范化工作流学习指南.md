## 第一章　为什么需要这套方法论

在 AI 工具快速普及的今天，代码生成的门槛已经大幅降低。但很多开发者发现，AI 虽然能快速写出代码，却经常出现以下问题：

> ⚠️ **使用 AI 开发时的常见困境**
>
> - AI 执行任务时跳过细节，说"完成了"但其实遗漏了关键逻辑
> - 没有预先规划，开发到一半发现数据库结构需要推倒重来
> - 需求描述模糊，AI 自行假设导致实现方向偏差
> - 任务粒度太大，完成后无法验收，问题累积到集成阶段才暴露
> - 缺乏自检机制，代码质量参差不齐

这套方法论的核心思想只有一句话：

> **你负责想清楚，AI 负责做清楚，文档负责记清楚。**代码是结果，决策和文档才是过程。把过程管好了，结果自然不会差。

### 角色重新定义

| 传统开发模式       | AI 深度参与开发模式 |
| ------------ | ----------- |
| 你：写代码        | 你：做决策、验收、沉淀 |
| 你：查文档、解决 Bug | 你：定义验收标准    |
| AI：辅助补全      | AI：执行、自检、汇报 |
| 质量靠个人经验      | 质量靠流程和自检清单  |

### 三条铁律

| 铁律    | 说明                      |
| ----- | ----------------------- |
| 文档先行  | 没有文档的阶段不算开始，没有产出的阶段不算结束 |
| 验收驱动  | AI 说完成不算完成，通过验收标准才算完成   |
| 问题不过夜 | 当前阶段发现的问题，必须在进入下一阶段前解决  |

## 第二章　全流程总览

整个工作流分为五个阶段：

```
想法 / 业务需求
    ↓
① 需求定义      → PRD 文档 + 术语表
    ↓
② 预开发规划    → AGENT.md + 数据库设计 + 接口文档 + 自检清单
    ↓
③ 迭代开发      → Phase 1 → Phase 2 → Phase 3 → Phase 4
    ↓
④ 质量收敛      → 三层自检 → 自检报告
    ↓
⑤ 复盘沉淀      → 提示词库 + 可复用模板
    ↓
✅ 可交付的产品
```

### 各阶段角色分工

| 阶段      | 你的职责        | AI 的职责     | 核心产出             |
| ------- | ----------- | ---------- | ---------------- |
| ① 需求定义  | 描述场景，定义验收标准 | 澄清遗漏，结构化输出 | PRD 文档           |
| ② 预开发规划 | 审阅拍板，技术决策   | 生成文档，规划执行  | AGENT.md + 自检清单  |
| ③ 迭代开发  | 确认清单，逐步验收   | 执行代码，自检汇报  | 可运行代码 + Phase 报告 |
| ④ 质量收敛  | 最终确认，交付裁决   | 多层自检，修复问题  | 自检报告 + 问题清单      |
| ⑤ 复盘沉淀  | 总结经验，更新模板   | 整理报告，提炼提示词 | 复盘文档 + 提示词库      |

## 第三章　需求定义阶段

**目标**：将模糊的业务想法转化为结构化的 PRD，消除所有歧义，为后续阶段提供清晰的北极星。

### 四步工作法

| 步骤               | 内容                                       |
| ---------------- | ---------------------------------------- |
| Step 1：业务全景摸底    | 按「用户角色 → 核心业务 → 部署交付 → 个性化」四个维度提问，挖掘所有场景 |
| Step 2：补全与确认     | AI 整理回答，补全遗漏，对歧义点标注 ❓ 并提供选项，你来拍板         |
| Step 3：生成 PRD 草稿 | 输出结构化 PRD，包含用户故事、业务流程、功能模块、验收标准          |
| Step 4：逐节审阅确认    | 你逐段审阅，有偏差当场修改，确认无误后 PRD 正式定稿             |

### PRD 文档结构（七个章节）

| 章节              | 内容说明                        |
| --------------- | --------------------------- |
| 一、产品定位          | 一句话描述系统是干什么的，核心价值是什么        |
| 二、用户角色体系        | 所有角色的定义、产生方式、权限范围、关键设计决策    |
| 三、核心功能模块        | 每个功能的详细流程、状态机、关键业务规则        |
| 四、非功能需求         | 部署要求、性能指标、移动端适配等            |
| 五、术语表（GLOSSARY） | 所有业务名词的精确定义，消除理解歧义          |
| 六、验收标准          | 每个功能点的可量化验收条件（Checklist 格式） |
| 七、本版本范围（Scope）  | 明确做什么、不做什么、哪些功能预留扩展         |

### 歧义消除技巧

需求定义阶段最容易遗漏的不是功能，而是边界和决策点。常见歧义类型：

- **数据归属问题**：某个数据属于全局还是某个业务实体？
- **状态流转问题**：某个状态能否回退？由谁触发流转？
- **权限边界问题**：A 角色能否查看 B 角色的数据（只读）？
- **并发场景问题**：多人同时操作同一资源时如何处理？
- **历史数据问题**：删除某条记录时，关联数据如何处理？

### 阶段完成标准

-  每个角色的核心操作都有明确描述
-  每个业务流程都有完整的状态流转
-  每个功能都有可量化的验收标准
-  所有业务歧义已消除，AI 能独立回答业务问题
-  你能用 3 分钟向陌生人说清楚这个系统

## 第四章　预开发规划阶段

**目标**：在写第一行代码之前，把所有技术决策做完，把执行地图画好。

### 为什么这个阶段最重要

```
代码写错了可以重写          → 成本：低
接口设计错了要改前后端      → 成本：中
架构设计错了要推倒重来      → 成本：高
数据库表结构错了牵连所有代码  → 成本：极高
```

### 六步规划顺序

| 步骤            | 内容                                  | 关键产出               |
| ------------- | ----------------------------------- | ------------------ |
| Step 1：需求理解确认 | AI 用自己的话复述需求，不允许照抄 PRD 原文，暴露理解偏差    | 歧义问题清单             |
| Step 2：技术选型   | 确定所有依赖和版本号，后续不再变动                   | 技术栈清单（含版本）         |
| Step 3：数据库设计  | 输出所有表的完整字段定义，含类型、索引、枚举值、关联关系        | docs/database.md   |
| Step 4：接口设计   | 输出所有接口的路径、权限、入参校验、响应格式、业务规则、错误码     | docs/api.md        |
| Step 5：执行计划   | 按 Phase 划分任务，输出每个 Phase 的文件清单和开发顺序  | docs/phase-plan.md |
| Step 6：规范固化   | 将所有规范写入 AGENT.md，各 Phase 自检清单写入独立文件 | AGENT.md + 自检清单    |

### AGENT.md 文件结构

AGENT.md 是放在项目根目录的 AI 工作规范文件，AI 每次对话前会自动读取。应包含：

1. 项目概述（1-3 行）
2. 技术栈速查（所有依赖和版本）
3. 项目目录结构速查
4. 数据库核心表速查
5. 接口统一规范（响应格式、错误码）
6. 执行纪律（开始前/执行中/完成后的行为规范）
7. 代码规范（必须遵守的规则和禁止事项）
8. 关键业务规则速查（并发控制、权限保护等）
9. 各 Phase 自检清单索引

### 自检清单文件结构

每个 Phase 有一份独立的自检清单（docs/checklist-phaseX.md），覆盖以下维度：

| 维度    | 检查内容示例                     |
| ----- | -------------------------- |
| 数据库   | 表结构完整性、索引是否添加、字段类型是否正确     |
| 接口    | 所有接口是否实现、入参校验是否完整、权限注解是否添加 |
| 业务规则  | 核心业务规则是否在代码中体现             |
| 权限边界  | 越权场景是否被正确拦截                |
| 并发安全  | 并发操作是否使用原子操作保护             |
| 代码质量  | 无调试代码、无空 catch、无硬编码魔法值     |
| 前端完整性 | 所有页面是否实现、路由守卫是否正确          |

## 第五章　迭代开发阶段

**目标**：按计划小步快跑，每个任务独立可验收，不积累问题。

### 核心原则：小步快跑

```
❌ 错误方式：「把整个 Phase 1 都做完」
   → 任务太大，AI 跳过细节无法被发现，问题积累到最后爆发

✅ 正确方式：「完成任务 1-1，我验收，再做任务 1-2」
   → 每步可验收，问题当场暴露，修复成本最低
   → 单次任务颗粒度：30 分钟内可验收
```

### 单任务执行节奏

| 步骤         | 操作                     | 注意事项                      |
| ---------- | ---------------------- | ------------------------- |
| 1. 下达任务    | 告诉 AI 要做什么，提供任务编号和具体要求 | 任务描述要具体，指向 AGENT.md 和自检清单 |
| 2. AI 列清单  | AI 列出本次任务的完整子任务清单      | 不允许 AI 跳过这步直接动手           |
| 3. 你确认清单   | 审阅子任务清单，确认无遗漏          | 这是关键步骤，缺项在这里补             |
| 4. AI 逐条执行 | 每完成一个子任务，输出 ✅ 确认       | 每条都要有文件路径说明               |
| 5. AI 自检   | AI 对照自检清单逐条核查          | 必须逐条，不允许笼统说「已检查」          |
| 6. 你验收     | 对照验收标准，提问边界场景          | 见下方「验收三步法」                |
| 7. 通过/修复   | 通过则进入下一任务，不通过则修复后重新自检  | 问题不过夜                     |

### 验收三步法

不要只看 AI 说「完成了」就通过，要做这三件事：

**① 对照清单核查**拿出该任务的自检清单，逐条确认是否打勾，有 ❌ 的立即要求修复。

**② 提问边界场景**针对本任务提出至少 2-3 个边界问题：

```
「如果用户传入非法参数，这个接口返回什么？」
「如果两个用户同时操作，会发生什么？」
「如果数据库连接失败，会怎样？」
「如果该记录不存在，返回什么错误码？」
「已经是最终状态的记录，再调用这个接口会怎样？」
```

**③ 抽查关键代码**

```
「把并发名额扣减的具体 SQL 给我看一下」
「把权限校验切面的代码给我看一下」
```

### 管理 AI 行为的执行纪律提示词

将以下内容写入 AGENT.md，或在每次任务开始时提醒 AI：

```
每次任务开始前，先列出完整子任务清单，等我确认后再动手。
每完成一个子任务，输出：✅ 已完成：[文件路径] - [具体做了什么]
不允许因为「类似」「差不多」跳过任何细节。
遇到不确定的地方先问我，不自行假设。
```

## 第六章　质量收敛阶段

**目标**：系统性地找出所有遗漏和问题，达到可交付标准。

### 三层自检体系

| 层级        | 触发时机           | 覆盖范围            | 目的      |
| --------- | -------------- | --------------- | ------- |
| 第一层：单任务自检 | 每个任务完成后立即执行    | 本任务涉及的所有细节      | 防止细节遗漏  |
| 第二层：阶段自检  | 每个 Phase 完成后执行 | 本 Phase 所有文件和接口 | 防止跨任务遗漏 |
| 第三层：全项目自检 | 所有 Phase 完成后执行 | 整个项目所有功能和安全性    | 确保整体可交付 |

### 第一层：单任务自检（4 步）

1. **对照需求逐条核查**：将任务要求逐条列出，每条标注 ✅/❌/⚠️，并说明在哪个文件哪一行实现
2. **代码质量自查**：无调试代码、无硬编码魔法值、异常是否处理、入参是否校验
3. **边界条件自查**：列出至少 3 个边界场景，说明代码是否已覆盖
4. **输出结论**：明确「本任务是否真正完成」，未完成则立即补充后重新执行步骤 1

### 第二层：阶段自检（7 个维度）

| 维度      | 检查内容                           |
| ------- | ------------------------------ |
| ① 文件完整性 | 列出本 Phase 应新建的所有文件，逐一确认存在且内容完整 |
| ② 接口完整性 | 所有接口是否实现、权限注解是否添加、返回格式是否统一     |
| ③ 数据库检查 | 所有表是否建好、索引是否添加、枚举值是否正确         |
| ④ 权限边界  | 越权场景（普通用户/赛事管理员/未登录）是否都被拦截     |
| ⑤ 边界场景  | 并发、超时、重复操作等边界场景是否处理            |
| ⑥ 代码规范  | 无调试代码、无空 catch、事务注解、异步注解       |
| ⑦ 自检结论  | 输出检查表，有 ❌ 项则修复后重新过清单           |

### 第三层：全项目自检（5 个维度）

| 维度         | 检查方式                          |
| ---------- | ----------------------------- |
| ① 功能完整性    | 对照 PRD 功能清单，逐条确认是否实现          |
| ② 接口全量核对   | 列出所有接口，按权限分组逐一确认实现            |
| ③ 核心业务链路模拟 | 模拟 3-5 条完整业务链路，逐步说明接口调用和数据库变化 |
| ④ 安全性检查    | 密码加密、JWT 过期、文件类型校验、SQL 注入防护   |
| ⑤ 前端页面完整性  | 列出所有页面路由，逐一确认实现且移动端适配正常       |

### 最终交付报告格式

全项目自检通过后，要求 AI 生成最终交付报告，包含：

- 总体结论（通过 / 未通过）
- 已实现功能清单（完整版）
- 已知问题与风险（所有 ❌ 项或 ⚠️ 风险点）
- 需要人工验证的项目
- 建议的手动测试用例（至少 5 条核心链路）

## 第七章　复盘沉淀阶段

**目标**：把经验固化为可复用资产，让下一个项目更快更好。

### 复盘三个核心问题

| 问题           | 目的             | 输出                    |
| ------------ | -------------- | --------------------- |
| 哪些提示词最有效？    | 复用有效提示词，减少调试成本 | 更新 PROMPTS-LIBRARY.md |
| AI 在哪里最容易出错？ | 下次在自检清单里加对应检查项 | 更新 checklist 模板       |
| 哪些决策最消耗时间？   | 下次在预开发阶段提前想清楚  | 更新 AGENT.md 模板        |

### 四类沉淀资产

| 资产类型     | 文件名                   | 内容说明                    |
| -------- | --------------------- | ----------------------- |
| 复盘文档     | RETROSPECTIVE.md      | 本项目的经验教训、踩过的坑、改进建议      |
| 提示词库     | PROMPTS-LIBRARY.md    | 本项目中效果最好的提示词，按场景分类      |
| 自检模板     | CHECKLIST-TEMPLATE.md | 通用自检模板，下个项目直接复制修改       |
| AGENT 模板 | AGENT-TEMPLATE.md     | 通用 AGENT.md 模板，下个项目直接套用 |

### 下个项目的启动流程

1. 复制 AGENT-TEMPLATE.md → 修改为新项目的 AGENT.md
2. 复制 CHECKLIST-TEMPLATE.md → 为新项目生成各 Phase 自检清单
3. 从 PROMPTS-LIBRARY.md 中找到对应场景的提示词直接使用
4. 对照 RETROSPECTIVE.md 中的踩坑记录，提前规避已知问题

## 第八章　快速参考手册

### 8.1　启动提示词

**预开发阶段启动：**

```
我即将给你一份完整的 PRD 文档。在你写任何一行代码之前，
请完成预开发阶段的全部工作（共 6 步）。
每步完成后等我确认，再进行下一步。

[粘贴 PRD 内容]
```

**Phase 开发启动：**

```
请读取 AGENT.md 和 docs/checklist-phase1.md，
列出 Phase 1 的完整子任务清单，等我确认后开始执行。
```

**单任务启动：**

```
请完成以下任务，先列出子任务清单等我确认，
再逐条执行，每条完成后标注 ✅：

[任务描述]
```

### 8.2　AI 跳过细节时的补救话术

| 发现问题                    | 补救话术                                |
| ----------------------- | ----------------------------------- |
| 按钮缺少 active/disabled 状态 | 「请检查所有按钮，补全 active 和 disabled 状态」   |
| 移动端没有适配                 | 「请逐一检查所有媒体查询断点，确认响应式未被破坏」           |
| CSS 有硬编码颜色残留            | 「请全局搜索硬编码颜色值，统一替换为 CSS 变量」          |
| 说完成但有文件没动               | 「请列出本次任务涉及的所有文件，逐一确认是否处理」           |
| 异常处理缺失                  | 「请检查所有 catch 块，确认有适当的错误处理而非空 catch」 |

### 8.3　常见边界场景提问清单

对任意接口/功能，提问以下问题来验收质量：

- 传入空值/null 时返回什么？
- 传入超长字符串时返回什么？
- 传入不存在的 ID 时返回什么（404 还是 500）？
- 两个用户同时操作同一条记录时会发生什么？
- 操作已经处于最终状态的记录时返回什么？
- 用户越权访问不属于自己的资源时返回什么？
- token 过期时返回 401 还是 403？
- 上传超大文件时返回什么错误？

### 8.4　文件目录规范

## 第九章　完整案例回顾

本指南对应的真实项目案例：**lz_sports 校园运动会报名系统**。

### 项目概述

| 项目要素  | 内容                                       |
| ----- | ---------------------------------------- |
| 技术栈   | Spring Boot 3.2 + Vue 3 + MySQL 8 + Redis 7（JDK 21） |
| 交付形式  | 前后端分开部署，后端 Jar 包 + 前端 Nginx 静态文件         |
| 核心角色  | 超级管理员 / 赛事管理员 / 普通用户 / 运动员（赛事级）          |
| 数据库规模 | 10 张表，42 个接口                             |
| 开发计划  | 4 个 Phase，预计 18 天 + 2 天联调                |

### 各阶段产出一览

| 阶段    | 关键产出                                    | 重要决策                            |
| ----- | --------------------------------------- | ------------------------------- |
| 需求定义  | PRD v1.0（7个章节）、术语表、Scope 说明             | 运动员身份是赛事级别的；普通用户零门槛注册           |
| 预开发规划 | AGENT.md、数据库设计（10张表）、接口文档（42个接口）、4份自检清单 | JDK 21；前后端分离部署；并发用原子 UPDATE 防超卖 |
| 迭代开发  | Phase 1-4 可运行代码、4份 Phase 完成报告           | 按 30 分钟粒度拆解任务；每步验收后再继续          |
| 质量收敛  | 三层自检全部通过、最终交付报告                         | 全项目接口全量核对；5条核心链路模拟测试            |

### 本案例消除的 5 个关键歧义

| 歧义点        | 最终决策                        |
| ---------- | --------------------------- |
| 运动员申请信息归属  | 用户表存基本信息，首次填写后自动带入，每次申请可修改  |
| 项目时间冲突校验范围 | 只检测同一赛事内的项目时间冲突，跨赛事不检测      |
| 报名上限设置权限   | 超级管理员创建赛事时设置，报名开始后不可修改      |
| 站内信已读未读    | 有已读/未读状态，导航栏显示未读数量角标（30秒轮询） |
| 赛事管理员数据权限  | 可查看所有赛事公开信息，只能操作被分配的赛事      |
